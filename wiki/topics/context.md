## 这个方向在解决什么

agent 的工作信息随步数增长：工具输出、环境观察、中间推理和历史对话不断累积，增长速度超过模型能低成本且可靠处理的范围。context window 即使足够长，注意力计算和 KV cache 的开销也随长度上升，已有研究（如 Lost in the Middle）观察到，长输入中间位置的信息更容易被模型忽略。因此每一步都要决定把哪些信息、以什么形式放进模型的输入。context 方向关心当前这一步的输入；保存在输入之外、按需取回的部分归 memory 方向。

## 概念地图

### 窗口装不下时怎么办

- 上下文压缩：摘要、裁剪、提示词压缩（LLMLingua 一类）。
- 检索式上下文：信息放在外部，只把当前需要的部分取回放进输入。

### 谁来决定放什么

- harness 管理的上下文：固定窗口、截断、按规则定期压缩。
- 模型自管理上下文：模型自己决定读入、写出和丢弃哪些内容。

### 长上下文本身

- 长上下文的可靠性：位置偏差（Lost in the Middle 一类），有效长度与标称长度的差距。
- 推理开销：KV cache 的体积、复用与淘汰。

### 上下文作为可迭代的对象

- 上下文工程：把系统提示、策略和经验条目当作可以持续修改和积累的内容（ACE 一类）。

## 关键争论

- 长上下文还是频繁压缩：把 context window 做长并保留全部历史，与保持短上下文并频繁压缩，哪条路线在成本和任务完成率上更划算；压缩时丢掉的信息事后能否找回。
- 模型自管理还是 harness 管理：上下文的取舍交给模型通过训练学会，还是由外部规则决定。前者需要合适的训练信号，后者依赖人工设计，换任务时要重新调。
- 标称长度和有效长度：模型声称支持的 context window，与它在多步任务里能稳定利用的长度之间差多少，该用什么任务来测。
